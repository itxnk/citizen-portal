DESC01 — Challenge
The Challenge
What the RFP requires — and the problems a traditional deployment cannot solve

❌ Traditional Monolith Limitations

  • Cannot scale individual components — the entire app scales or none
  • A single bug can bring down the whole system
  • Deployments require full downtime or risky in-place updates
  • No automated failover — one server failure = outage
  • Manual infrastructure provisioning — error-prone, unrepeatable
  • No observability — problems discovered by users, not dashboards

✅ RFP Requirements

  • Containerise monolithic components into isolated microservices
  • Demonstrate auto-scaling under load (HPA)
  • Infrastructure as Code — reproducible in one command
  • GitOps continuous deployment — no manual kubectl apply
  • Prometheus + Grafana observability
  • Zero-downtime rolling deployments
  • Multi-AZ high availability on AWS

DESC05 — AWS Infrastructure
AWS Infrastructure
Every component is managed, highly-available, and provisioned by Terraform
AWS ap-south-1 (Mumbai) ├── VPC 10.0.0.0/16 │ ├── Public subnets (2 AZ) — ALB, NAT Gateway │ ├── Private subnets (2 AZ) — EKS worker nodes │ └── Isolated subnets(2 AZ) — RDS, ElastiCache │ ├── EKS Cluster (Kubernetes 1.29) │ ├── Managed node group: t3.medium × 3 baseline (auto-scale to 10) │ ├── ALB Ingress Controller — routes /* and /api/* │ ├── EBS CSI Driver — Prometheus PVC │ └── desc-app namespace — 5 Deployments, 5 HPAs, 5 ServiceMonitors │ ├── RDS PostgreSQL 15 — Multi-AZ, encrypted, private subnet │ ├── ElastiCache Redis 7 — Cluster mode, TLS in transit, private subnet │ └── Supporting: Secrets Manager · ECR · WAF · Route 53 · CloudTrail

Why AWS EKS?

Managed Kubernetes control plane — no etcd to maintain. Native integration with ALB controller, EBS CSI, VPC CNI. EKS Managed Node Groups handle OS patching automatically.

Why Multi-AZ?

RDS fails over automatically in <90 seconds. Redis has read replicas in a second AZ. EKS nodes span two AZs — a single AZ failure leaves the system fully operational.

Why isolated subnets for data?

RDS and Redis have no internet route — not even outbound. Only the EKS node security group can reach them on the exact port. Defence-in-depth.

DESC06 — Auto-Scaling
Auto-Scaling in Action
Horizontal Pod Autoscaler + Cluster Autoscaler — two levels of elasticity

HPA Configuration per Service

Records Service ★ min 2 max 15 target 50% CPU
User Service min 2 max 10 target 50% CPU
Notification Service min 2 max 10 target 60% CPU
Gateway + Frontend min 2 max 10 target 50–60% CPU

Scale-Up: 15s · Scale-Down: 5m

Asymmetric windows are deliberate — scale up fast (protect user experience), scale down slowly (avoid thrashing under bursty traffic).

DESC07 — Infrastructure as Code
Infrastructure as Code — Terraform
The entire AWS environment is reproducible with a single command
terraform apply ├── module.vpc — VPC, subnets, NAT ├── module.security_groups — SGs (least-privilege) ├── module.eks — EKS cluster + nodes ├── module.rds — PostgreSQL Multi-AZ ├── module.elasticache — Redis cluster + TLS └── helm_release.argocd — ArgoCD on EKS Remote state: S3 bucket + DynamoDB lock Secrets: AWS Secrets Manager

Why Terraform?

Declarative, state-tracked, provider ecosystem covers AWS + Helm + Kubernetes in one tool. Modular structure makes each layer independently testable. terraform plan shows exactly what will change before anything happens.

Why not CloudFormation or CDK?

CriterionTerraform ✅CloudFormation ❌
Multi-cloud portabilityWorks with any providerAWS-only
Helm / Kubernetes supportNative providers — deploy ArgoCD in same planRequires custom resources or CDK
State managementS3 + DynamoDB lock — team-safeBuilt-in but less flexible
Module ecosystemTerraform Registry — battle-tested modulesNo equivalent registry
Plan previewterraform plan — diff before applyChange sets (more verbose)
Industry adoptionDe-facto IaC standardAWS-specific teams only
DESC08 — GitOps
GitOps with ArgoCD
Git is the single source of truth — no manual deployments, ever

How it works

1. Dev merges PR
→
GitHub Actions CI
2. Image pushed to DockerHub
→
sha-abc1234 tag
3. yq updates values.yaml
→
git commit [skip ci]
4. ArgoCD detects diff
→
Self-heals to Git state
5. Rolling update, zero-downtime
→
Live ✓

Rollback = one git revert

Bad deployment? git revert HEAD — ArgoCD detects the revert within 3 minutes and rolls back automatically. MTTR <15 minutes.

ArgoCD Configuration

syncPolicy: automated: prune: true # remove deleted resources selfHeal: true # fix manual changes syncOptions: - CreateNamespace=true ignoreDifferences: # HPA current replicas - group: autoscaling/v2 kind: HorizontalPodAutoscaler jsonPointers: - /spec/replicas

Why GitOps? Why not direct kubectl?

  • Audit trail — every deployment is a git commit
  • Drift detection — ArgoCD flags manual changes
  • Self-healing — deleted pod or config is restored automatically
  • No credentials on CI runner — ArgoCD pulls from Git, never pushed to
DESC09 — CI/CD
CI/CD Pipeline — GitHub Actions
Path-filtered per-service CI + a parallel matrix release workflow

Per-Service CI (on every PR / push)

paths: app/gateway/**
→
only triggers for that service
job: lint-and-test
ruff check . # linting
pytest tests/ -v # unit tests (no infra)

job: docker-build (needs: lint-and-test)
docker/build-push-action push: false

Release Workflow (on merge to main)

strategy.matrix: [gateway, user-svc, records-svc, …]
→ Build all 5 images in parallel
→ Push: sha-abc1234 + latest
→ yq: values.yaml image.tag = sha-abc1234
→ git commit [skip ci] — ArgoCD picks it up

Why two separate tags?

sha-abc1234
Pinned in Helm values.yaml — ArgoCD always deploys this exact image. Rollback = revert this tag.
latest
Used by Docker Compose for local dev — always gets the newest build without any manual config.

What every service CI tests

  • Ruff linting — PEP 8 + import ordering
  • All DB calls mocked — no live PostgreSQL in CI
  • All Redis calls mocked — no live Redis in CI
  • Prometheus registry cleaned between tests — no duplicate metric errors
  • Docker image builds successfully (push: false in CI)
5 CI workflows
1 release workflow
34 unit tests total
Path-filtered — no wasteful rebuilds
DESC10 — Security
Security — Defence in Depth
Seven independent security layers — compromise one, the rest still hold
🛡️

AWS WAF → ALB

OWASP managed rule group + rate limiting (1000 req/5min) before any traffic reaches EKS. SQL injection, XSS, and bad bot rules enabled by default.

🔒

Isolated Network Tiers

RDS and Redis sit in subnets with no internet route — outbound or inbound. Only EKS node SGs reach them on the exact port, referenced by SG ID (not CIDR).

🗝️

Secrets Management

DB passwords and Redis auth tokens generated by Terraform's random_password and stored in AWS Secrets Manager. Never in Git, never in container images.

👤

Non-Root Containers

All 5 images run as UID 1000 (appuser). runAsNonRoot: true and allowPrivilegeEscalation: false in all Kubernetes securityContexts.

🔐

TLS Everywhere

ALB terminates HTTPS (ACM certificate). Redis TLS in-transit (transit_encryption_enabled). RDS encrypted at rest (AES-256) and in transit.

📋

IRSA — Least-Privilege IAM

IAM Roles for Service Accounts (IRSA) — each pod gets only the AWS permissions it actually needs. No shared credentials, no wildcard policies.

DESC12 — Technology Choices
Technology Choices & Rationale
Every tool was selected for a specific reason — not because it is popular
LayerTool / VersionWhy This, Not an Alternative?
CloudAWS EKS 1.29Managed K8s control plane (no etcd to maintain). Native ALB controller, EBS CSI, VPC CNI. RDS + ElastiCache as managed stateful services — no DB ops burden on the team.
IaCTerraform ≥ 1.6Declarative + state-tracked. Provider ecosystem covers AWS + Helm + K8s in one plan. terraform plan shows changes before they happen. CloudFormation is AWS-only and verbose.
GitOps CDArgoCD v2.10Kubernetes-native; self-healing (selfHeal: true); drift detection; audit trail in Git. Flux is equally valid — ArgoCD chosen for its visual UI (demo-friendly) and wider adoption.
CIGitHub ActionsNative to GitHub, zero infrastructure to maintain. Path-filtered triggers prevent wasteful rebuilds. Matrix strategy builds all 5 images in parallel on release.
API FrameworkFastAPI (Python 3.12)Async-native with asyncpg. Auto-generates OpenAPI docs. Prometheus client integrates directly. Django/Flask too heavyweight; synchronous frameworks create event loop contention.
DatabasePostgreSQL 15 (RDS)ACID guarantees, asyncpg async driver, Multi-AZ failover (<90s). MySQL lacks some JSON operators used. MongoDB would add operational complexity for structured relational data.
Cache/PubSubRedis 7 (ElastiCache)Unified cache-aside + pub/sub in one service. Memcached lacks pub/sub. Redis 7 cluster mode gives HA without application changes.
ObservabilityPrometheus + GrafanaDe-facto Kubernetes observability stack. kube-prometheus-stack deploys everything via one Helm chart. ServiceMonitor CRDs auto-discover all services. DataDog and New Relic cost 10× more with vendor lock-in.
Container RegistryDockerHubFree public tier sufficient for demo; no additional AWS costs. ECR would require IAM auth on CI runners — adds complexity without benefit at this scale.
Load Testingk6 + Locustk6 for precise, scriptable VU ramps; Locust for web UI live demo. JMeter is GUI-heavy and Java-dependent — poor fit for CI pipelines.
